# Managed hosting for ChatGPT acceptance

This document is the deployment contract for the stable HTTPS Development Intelligence service used by ChatGPT.

Development Intelligence is a long-running Node + Git service. Use a managed container/web-service host that can run the repository Dockerfile, provide a stable HTTPS hostname, inject secrets, and preserve a running process. Serverless function hosting is not the preferred production shape because DI performs Git checkout/analysis work and the OAuth authorization-code exchange is intentionally short-lived process state.

## Recommended deployment shape

A managed Docker web service such as Render or Railway is appropriate. The repository Dockerfile now honors a platform-provided `PORT` automatically and binds to `0.0.0.0` on hosted platforms.

For pre-merge PR #4 acceptance, deploy branch:

```text
feat/chatgpt-oauth-publishing
```

After PR #4 is accepted and merged, change the production deployment branch to:

```text
main
```

Do not merge PR #4 merely to make hosting easier; the stable hosted candidate is part of the merge acceptance evidence.

## Required environment values

Set these on the host:

```text
DEVINT_AUTH_MODE=oauth
DEVINT_OWNER_PASSWORD=<choose a strong password>
DEVINT_SESSION_SECRET=<generate a long random secret>
DEVINT_PUBLIC_BASE_URL=https://<the stable public hostname>
DEVINT_OAUTH_ALLOWED_REDIRECT_ORIGINS=https://chatgpt.com
DEVINT_OAUTH_SCOPES=development-intelligence.read
DEVINT_ALLOWED_HOSTS=<hostname only, no https:// prefix>
```

Do not set `DEVINT_COOKIE_SECURE=0` on the hosted HTTPS service.

`DEVINT_SESSION_SECRET` may be generated by the hosting provider or with a password manager / cryptographically secure random generator. Rotating it intentionally invalidates existing browser sessions, OAuth access/refresh tokens, and dynamically registered OAuth client IDs.

## Project registry without a mounted file

Managed hosts do not need to mount `/config/projects.json`. Supply the registry as the secret environment variable `DEVINT_PROJECTS_JSON`.

For PR #4 acceptance, this is a useful minimal registry:

```json
{
  "Development-Intelligence": {
    "repository": "https://github.com/pyralisxc/Development-Intelligence.git",
    "defaultRef": "refs/heads/main",
    "allowedRefs": [
      "refs/heads/main",
      "refs/heads/feat/chatgpt-oauth-publishing"
    ],
    "credential": {
      "type": "token-env",
      "tokenEnv": "DEVINT_GITHUB_TOKEN",
      "username": "x-access-token"
    }
  }
}
```

Store that JSON as one environment value, not in Git.

Also set:

```text
DEVINT_GITHUB_TOKEN=<read-only GitHub token>
```

For a private repository, the token must be able to read the repositories DI is configured to inspect. Prefer a fine-grained/read-only credential limited to the required repositories. Development Intelligence itself does not need GitHub write permission.

To give DI access to additional projects later, add entries to `DEVINT_PROJECTS_JSON` and ensure the Git credential can read those repositories. Keep the registry operational: repository URLs, refs, credentials, runtime origins, and technical sources only. Do not encode product ontology or desired behavior in it.

## Health and OAuth checks

The host health check path is:

```text
/health
```

After the service has a stable HTTPS hostname, verify:

```text
GET https://<host>/health
GET https://<host>/.well-known/oauth-protected-resource/mcp
GET https://<host>/.well-known/oauth-authorization-server
```

Then confirm unauthenticated MCP access fails closed:

```text
POST https://<host>/mcp
```

It should return `401` with an OAuth protected-resource challenge.

## Render-specific setup

If using Render:

1. Connect the Render app/plugin to ChatGPT, or open the Render dashboard.
2. Create a **Web Service** from `pyralisxc/Development-Intelligence`.
3. Select branch `feat/chatgpt-oauth-publishing` for PR #4 acceptance.
4. Runtime: **Docker**. The repository root Dockerfile is sufficient.
5. Health check path: `/health`.
6. Add the environment values listed above. Treat `DEVINT_OWNER_PASSWORD`, `DEVINT_SESSION_SECRET`, `DEVINT_PROJECTS_JSON`, and `DEVINT_GITHUB_TOKEN` as secrets.
7. Use a stable public HTTPS service URL. Avoid an intentionally sleeping/ephemeral service for the final release connection; OAuth and cross-session agent access should not depend on a preview tunnel.
8. Once the service URL is assigned, set `DEVINT_PUBLIC_BASE_URL` and `DEVINT_ALLOWED_HOSTS` to that exact deployment hostname, then redeploy.

The Docker image does not require a persistent disk or graph database. Scratch Git checkouts are disposable.

## ChatGPT setup after hosting

Only after all hosted discovery checks pass:

1. On ChatGPT web, enable Developer mode if required for the account/workspace.
2. Go to **Settings -> Apps -> Create** (or **Workspace settings -> Apps -> Create** for an admin/owner workspace flow).
3. MCP endpoint: `https://<host>/mcp`.
4. Authentication: **OAuth**.
5. Choose **Scan Tools**.
6. Complete DI owner sign-in and consent when ChatGPT opens the OAuth flow.
7. Create the draft app.
8. In a fresh chat, prove a DI-only read.
9. In one prompt, select/use both Development Intelligence and GitHub and run the mixed-source acceptance prompt from `docs/chatgpt-publishing.md`.
10. Repeat the mixed-source test in a fresh Work session when Work is in release scope.

On a Business/Enterprise/Edu workspace, an Admin/Owner can publish the app after acceptance. On Pro/consumer surfaces, keep Developer mode enabled and use the available developer/custom-app path; publication controls can differ by plan.

## Release cleanup

After PR #4 passes hosted acceptance and is merged:

- deploy `main` rather than the feature branch;
- optionally remove `refs/heads/feat/chatgpt-oauth-publishing` from `allowedRefs`;
- rerun OAuth discovery and mixed DI + GitHub acceptance against the production `main` deployment;
- only then create the intended Git tag/GitHub Release.
