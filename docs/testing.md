# Development acceptance and test intelligence

## Development approach

Build the complete requested outcome and use DI on real repositories and ordinary engineering questions to assess it. Do not add tests, fixtures, test-only workflows, or proof machinery by default. The repository builds the product through `npm run build`; its own historical test suite and test-only automation are no longer part of the active development line. Previous versions remain available through Git history.

The product's ability to understand tests and correlate source-derived facts with run evidence in inspected repositories remains supported. Removing DI's own test suite does not remove those intelligence features.

## Source-derived execution facts and run observations

DI's source-execution fact analyzer (`src/intelligence/sourceExecutionFacts.ts`) independently derives `must-on-success`, `may-on-success`, `never-on-success` or `unknown` reachability for supported test assertions from exact source, test-declaration identity and a bounded TypeScript/JavaScript AST control-flow model. Positive `must-on-success` is a conditional source fact for the supported modeled paths—not a runtime observation—and should not be downgraded to an arbitrary candidate solely because no test run was supplied. Unsupported constructs, ambiguous bindings, nested callback effects and unknown completion behavior remain explicit. A non-overriding no-catch `try/finally` can preserve successful-path proof; a catch or finalizer that can mask failures may not.

The exact-source `get_test_claim_report` exposes source-fact population, proof fingerprint, location samples and unsupported counts separately from test outcomes. Ordinary source-execution questions reuse that report rather than implement another proof model. The operator-owned Node test worker can execute exact tracked Node tests and correlate native TestStream v2 pass/fail/skip/TODO events to a unique source test. A mandatory source assertion plus an observed passing direct run permits **run-scoped inferred execution**; an arbitrary supplied report remains reported/unattested. Neither inference alone proves an individual assertion's expected value, a real network/database write, or independent test replacement. Simulated dependencies still execute code, but do not prove the provider's external effect.

Preserve separate `sourceFactsSha256` (stable current-revision source proof) and `factsSha256` (source-plus-run assessment), and report run identity, code revision, analyzer, environment, mocks and observations when available. A missing CI/run attachment means **run evidence unavailable to that projection**, never that no tests ran. Establish test execution from genuine authenticated CI artifacts or direct witnessed runs when applicable. Independently audit positive source facts against real instrumentation and negative controls, then broaden compiler-grounded cross-function reachability only after measuring false positives, missing facts and unknowns. Do not double-count one passing test both as the premise and as independent confirmation of the same derived execution fact.

### Maintained test-claim reports

When `test-claim-catalog` is supplied, analysis writes one deterministic bundle at `.development-intelligence/test-claims` by default. `catalog-v1.json` is the normalized caller source-fact population, `report-v1.json` is the exact same evaluator result returned by analysis, and `manifest-v1.json` binds both digests to the exact source revision, graph identity, analyzer and evaluator versions, DI producer commit, normalized scope/config fingerprint, and population counts. Invalid or incomplete populations produce a retained `diagnostic` receipt rather than a successful redundancy conclusion. The composite action exposes the path, digest, status, and immutable artifact name and uploads the three-file bundle; this publication is evidence retention, not a success gate or deletion recommendation.

`graphCli test-claims` is the local read-only projection. It requires an expected exact source revision and report digest, validates the manifest, catalog, report, producer and evaluator identities, and returns stable pages whose identity and whole-population counts remain bound to the same digest. Missing reports return `available: false`; stale, mismatched, or tampered reports fail closed. Historical artifacts remain immutable receipts, while a new exact-source analysis creates a new current report.

Authenticated agents use `get_test_claim_report` with `project`, an immutable source `ref` (or exact `graphId`), and normalized `sourcePrefixes`/`sourceSuffixes`. DI checks out that one authorized revision, derives the catalog in memory with the same generic producer, and evaluates it against the same graph. No catalog commit, repository collector execution, or artifact import is required for an ordinary query. Results preserve explicit unsupported files/sites and return stable pages bound to scope, catalog/report digests, evaluator identity, and deployed DI producer commit. Page zero establishes the projection digest; every later page requires it as `expectedReportDigest`. Historical action artifacts and separately retained schema-v1 catalogs remain optional immutable CI receipts rather than query prerequisites.

The optional `populationDetail: "summary"` reduces repeated population diagnostics on each page: completeness flags and the discovery contract remain visible, while `detailsOmitted: true` and `detailCounts` disclose omitted fields. The default `"full"` is unchanged. To request all population diagnostics, repeat the same project, immutable revision and scope with `populationDetail: "full"` (or omit it) and set `expectedReportDigest` to the summary's `identity.projectionSha256`. A mismatch fails rather than silently returning different evidence. **Population diagnostics are not paginated:** every full page includes all of them, regardless of `pageSize`, so a large response can exceed transport limits and prevent full recovery. There is currently no bounded population-detail retrieval; a narrower scope creates a different report and digest and cannot recover the original report's diagnostics. Summary changes presentation only; it neither changes the digest nor avoids source recomputation.

CardForge can continue to emit catalog schema version 1 for maintained CI history. The action inputs are `test-claim-catalog`, optional `parity-contract`, and a report-path prefix (default `.development-intelligence/test-claims`). The action writes only to a run/attempt/job-owned child directory and never recursively clears caller content. Multiple invocations in the same job must supply distinct report-path prefixes because they share that job-owned suffix. Its artifact is named `development-intelligence-test-claims-<source-revision>-<manifest-digest>` and contains exactly `manifest-v1.json`, `catalog-v1.json`, and `report-v1.json`; action outputs expose the actual run path, digest, status, and artifact name. These retained files are historical evidence; current agent queries derive from exact source directly.
